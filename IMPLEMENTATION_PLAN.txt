# 0. Decisions locked before writing code

## 0.1 Tech stack (as recommended in the spec, with versions)

| Layer | Choice | Why |
|---|---|---|
| Framework | **Next.js 15 (App Router) + TypeScript** | Server routes keep API keys server-side; one deployable |
| UI | **Tailwind CSS + shadcn/ui** | Matches "Stripe/Linear clarity" direction |
| DB / Auth / Storage | **Supabase (Postgres + Auth + Storage)** | RLS gives per-business row isolation for free |
| AI | **Anthropic API** (`@anthropic-ai/sdk`) behind `/api/ai/*` route handlers | Spec: never call from browser |
| Payments | **Razorpay** (Orders + Subscriptions + Webhooks) | India-first, spec requirement |
| PDF | **React-PDF (`@react-pdf/renderer`) server-side** | Deterministic, no headless Chrome on Vercel |
| Email | **Resend** (or Brevo) | Send documents + reminders |
| Rate limit | **Upstash Redis** (`@upstash/ratelimit`) | Serverless-safe counters |
| Errors | **Sentry** | Spec: application error monitoring |
| Charts | **Recharts** | Dashboard + admin analytics |
| Validation | **Zod** (shared client + server schemas) | Spec: validate on client AND server |
| Money math | **decimal.js** or integer paise | Never use JS floats for totals |
| Hosting | **Vercel** | Spec recommendation |

## 0.2 Non-negotiable architecture rules

1. **AI never touches money.** All amounts, tax, discount, and totals are computed by one pure TypeScript module (`lib/calc/totals.ts`) that is unit-tested. The model may *suggest* a price — it is inserted only after explicit user confirmation.
2. **All money is stored as integers (paise).** `amount_paise BIGINT`. Format only at the display/PDF layer.
3. **Every AI call is: authenticated → rate-limited → credit-checked → executed → logged.** In that order, server-side. No exceptions.
4. **Subscription state is only ever changed by a verified Razorpay webhook**, never by the browser redirect.
5. **RLS on every table.** A row is readable only if `business_id = auth.uid()`'s business. Admin routes use the service-role key and a separate `is_admin` check.
6. **No fake UI.** Every list page ships loading / empty / error / populated states before it is called done.

## 0.3 AI model & cost decision (make this call now)

Pricing per 1M tokens (as of 2026-08-09):

| Model | Model ID | Input | Output | Use for |
|---|---|---|---|---|
| Claude Opus 5 | `claude-opus-5` | $5.00 | $25.00 | Full quotation generation from a brief, complex editing commands |
| Claude Sonnet 5 | `claude-sonnet-5` | $3.00 (**$2.00 intro until 2026-08-31**) | $15.00 (**$10.00 intro**) | Same tasks, high volume, cheaper |
| Claude Haiku 4.5 | `claude-haiku-4-5` | $1.00 | $5.00 | Rewrite/shorten/professionalize/translate selected text |

**Recommended routing** (implement as a config map, not hardcoded strings):

```ts
// lib/ai/models.ts
export const AI_MODELS = {
  QUOTATION_GENERATE: 'claude-opus-5',   // highest value, worth the quality
  INVOICE_ASSIST:     'claude-opus-5',
  TEXT_REWRITE:       'claude-haiku-4-5', // shorten / professionalize / translate
  REMINDER_DRAFT:     'claude-haiku-4-5',
} as const;
```

Start on Opus 5 for the flagship "Generate with AI" flow — it is your differentiator and the spec calls it "main differentiation and premium value." Route the cheap, high-frequency text tools to Haiku. Revisit after you have 2 weeks of real `ai_usage_logs` data. Downgrading is a one-line config change because of the map above.

**Credit model:** 1 AI credit = 1 successful AI request (simple for users to understand), but you additionally log real tokens and estimated USD cost per request so you can price correctly. Free = 15 credits/month. Premium = 500 credits/month.

# 3. Database schema (Phase 1 deliverable)

All tables carry `business_id UUID NOT NULL REFERENCES businesses(id)` and have RLS enabled.

| Table | Purpose | Key columns |
|---|---|---|
| `businesses` | Business profile & branding | `owner_user_id`, `name`, `logo_url`, `address`, `gstin`, `currency`, `quote_prefix`, `invoice_prefix`, `next_quote_no`, `next_invoice_no`, `default_tax_rate`, `default_terms`, `signature_url`, `brand_color` |
| `customers` | Lightweight directory | `name`, `company`, `email`, `phone`, `address`, `gstin`, `archived_at` |
| `products` | Reusable catalog | `name`, `description`, `unit`, `default_price_paise`, `tax_rate`, `default_discount_pct` |
| `quotations` | Sales document | `number`, `customer_id`, `issue_date`, `valid_until`, `status`, `subtotal_paise`, `discount_paise`, `tax_paise`, `total_paise`, `notes`, `scope`, `deliverables`, `exclusions`, `terms`, `converted_invoice_id` |
| `quotation_items` | Line items | `position`, `name`, `description`, `qty`, `rate_paise`, `tax_rate`, `discount_pct`, `line_total_paise` |
| `invoices` | Payment request | `number`, `customer_id`, `quotation_id`, `issue_date`, `due_date`, `status`, totals…, `amount_paid_paise`, `balance_paise` |
| `invoice_items` | Line items | same shape as quotation_items |
| `payments` | Money received | `invoice_id`, `amount_paise`, `paid_at`, `method`, `reference`, `razorpay_payment_id`, `source` (`manual`\|`razorpay`) |
| `share_links` | Public tokens | `doc_type`, `doc_id`, `token_hash`, `expires_at`, `viewed_at`, `view_count` |
| `document_events` | Activity timeline | `doc_type`, `doc_id`, `event` (created/sent/viewed/accepted/rejected/paid/edited), `actor`, `meta` |
| `plans` | Plan catalog | `code`, `name`, `price_paise`, `doc_limit`, `ai_credit_limit`, `features JSONB` |
| `subscriptions` | Per-business plan state | `plan_code`, `status`, `current_period_start/end`, `razorpay_subscription_id`, `cancel_at_period_end` |
| `usage_counters` | Metering, resets per period | `period_start`, `period_end`, `docs_used`, `ai_credits_used` |
| `ai_usage_logs` | Cost & audit | `user_id`, `feature`, `model`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `estimated_cost_usd`, `latency_ms`, `status`, `error_code` |
| `webhook_events` | Idempotency ledger | `provider`, `event_id UNIQUE`, `payload JSONB`, `processed_at`, `status` |
| `admin_audit_log` | Admin action trail | `admin_user_id`, `action`, `target_type`, `target_id`, `reason`, `before`, `after` |
| `app_users` | Role flags | `user_id`, `role` (`user`\|`support`\|`admin`), `suspended_at` |

**Critical constraints**
- `UNIQUE (business_id, number)` on quotations and invoices.
- Document numbering via a Postgres function with `SELECT ... FOR UPDATE` on `businesses` — never generate numbers in JS (race conditions produce duplicates).
- `webhook_events.event_id` UNIQUE — this single index *is* your idempotency guarantee.
- Generated column or trigger keeping `invoices.balance_paise = total_paise - amount_paid_paise`.

**RLS pattern (apply to every business-scoped table):**
```sql
alter table customers enable row level security;
create policy "own business" on customers
  for all
  using  (business_id = (select id from businesses where owner_user_id = auth.uid()))
  with check (business_id = (select id from businesses where owner_user_id = auth.uid()));
```
Then **write a test** that logs in as business A and asserts a `SELECT` of business B's rows returns zero. This is the single highest-value security test in the product.

## Phase 3 — Documents: Quotations & Invoices (Week 4–6) ⭐ the heart of the product

### 3.1 The calculation engine (build and test this FIRST)

```ts
// lib/calc/totals.ts — pure, no I/O, no AI, no DB
export type LineInput = {
  qty: number;            // supports decimals (e.g. 2.5 hours)
  ratePaise: number;
  discountPct: number;    // 0–100
  taxRatePct: number;     // 0, 5, 12, 18, 28
};
export type Totals = {
  subtotalPaise: number; discountPaise: number;
  taxPaise: number; totalPaise: number;
  taxBreakup: { ratePct: number; taxablePaise: number; taxPaise: number }[];
};
export function computeTotals(
  lines: LineInput[],
  docDiscountPct: number,
  opts: { taxMode: 'exclusive' | 'inclusive'; roundTo: 'unit' | 'none' }
): Totals;
```

Rules: compute per line → apply line discount → apply document-level discount proportionally → compute tax **per tax-rate bucket** (GST needs the breakup on the PDF) → round once, at the end, half-up. Test: zero-qty lines, 100% discount, mixed tax rates, 3-decimal quantities, rounding at 0.5 paise, ₹0 invoices, very large values.

### 3.2 Quotation module
- Auto-generated number from the business prefix + counter (Postgres function, `FOR UPDATE`).
- Editor: customer select, issue date, valid-until date, line items table (keyboard-first: Tab moves cell to cell, Enter adds a row), live totals panel.
- Long-form fields: notes, project scope, deliverables, exclusions, payment terms, T&C.
- Statuses: `draft → sent → viewed → accepted | rejected | expired`. Expiry set by a cron job on `valid_until`.
- Actions: duplicate, delete (draft only), **convert to invoice** (one click, copies items + totals, links both records).
- **Autosave** drafts (debounced 2s) + `beforeunload` warning on unsaved changes.

### 3.3 Invoice module
- Create manually, from AI, or from an accepted quotation.
- Number, issue date, due date, tax/GST, discount, payment terms.
- Statuses: `draft → sent → viewed → partially_paid | paid | overdue`. Overdue is set nightly by cron comparing `due_date` to today when `balance_paise > 0`.
- Payment history table + remaining balance, always derived, never hand-edited.
- Duplicate invoice. One-click reminder (wired to email in Phase 4).

### 3.4 Shared UX (the "feels premium" list from the spec)
- Global search across customer name, quote number, invoice number (Postgres `pg_trgm` index).
- Filters: date range, status, customer, overdue-only.
- Row actions from the list page: duplicate, copy share link, download PDF.
- **Activity timeline** on every document, written to `document_events` on: created, sent, viewed, accepted, rejected, paid, edited.

Acceptance
- [ ] `totals.ts` has 100% branch coverage and a property-based test (sum of line totals + tax − discount == grand total, always).
- [ ] Convert-to-invoice reproduces totals to the paise.
- [ ] Two concurrent quote creations produce two different numbers (test with parallel requests).
- [ ] Autosave survives a hard tab close and restores on reopen.

## Phase 5 — Payments (Week 9–10)

Tasks
1. **Manual payment recording**: date, amount, method (cash/UPI/bank/cheque/card/other), reference note. Partial payments allowed. Recompute `amount_paid` / `balance` / status in one DB transaction.
2. **Razorpay for invoice payment**: `POST /api/payments/order` creates a Razorpay Order for the invoice balance → checkout modal on the public invoice page or in-app.
3. **Webhook `/api/webhooks/razorpay`** — this is the source of truth:
   - Read the **raw body** (Next.js: `await req.text()`, do not parse first).
   - Verify signature: `crypto.createHmac('sha256', RAZORPAY_WEBHOOK_SECRET).update(rawBody).digest('hex')` compared with `x-razorpay-signature` using `crypto.timingSafeEqual`.
   - Insert into `webhook_events` with `event_id` UNIQUE → duplicate insert = already processed → return 200 immediately (**idempotency**).
   - Handle `payment.captured`, `payment.failed`, `order.paid`, `subscription.activated`, `subscription.charged`, `subscription.halted`, `subscription.cancelled`.
   - Always return 200 for handled-or-ignored; return 5xx only on genuine processing failure so Razorpay retries.
4. Auto-update invoice status and balance only after a verified webhook. The browser redirect updates nothing — it only shows an optimistic "processing" state.
5. Payment receipt email + confirmation screen; payment activity history on the invoice.
6. Reconciliation view for the admin: webhook events vs payments rows, mismatch list.

Acceptance
- [ ] Replaying the same webhook 5× creates exactly one payment row.
- [ ] A tampered signature is rejected with 400 and logged.
- [ ] Partial payment of ₹4,000 on a ₹10,000 invoice → status `partially_paid`, balance ₹6,000.
- [ ] Test-mode payment flows end to end and lands in the invoice timeline.

## Phase 6 — AI features (Week 11–13) ⭐ the differentiator

### 6.1 Server-side AI client

```ts
// lib/ai/client.ts  — SERVER ONLY
import Anthropic from '@anthropic-ai/sdk';
export const anthropic = new Anthropic(); // reads ANTHROPIC_API_KEY
```

### 6.2 The mandatory pipeline for every AI route

```
requireUser()          → 401 if not authenticated
rateLimit(userId)      → 429 (Upstash sliding window, e.g. 10 req / 60s)
requireCredits(1)      → 402 with an upgrade CTA if the period allowance is exhausted
countTokens(prompt)    → 413 if the request is absurdly large (guards cost)
call Anthropic         → with prompt caching + structured output
logAiUsage(...)        → tokens, cost, latency, status — ALWAYS, success or failure
incrementCredits(1)    → only on success
return result          → to the client for review; never auto-applied to money fields
```

`requireCredits` must be an atomic DB operation (`UPDATE usage_counters SET ai_credits_used = ai_credits_used + 1 WHERE ... AND ai_credits_used < limit RETURNING *`) so two parallel tabs cannot both slip past the limit.

### 6.3 AI Quotation Assistant — structured output, not free text

The model returns a **schema-validated object**, so the UI can render it into the editor with zero parsing:

```ts
import { z } from 'zod';
import { zodOutputFormat } from '@anthropic-ai/sdk/helpers/zod';

const QuotationDraft = z.object({
  title: z.string(),
  lineItems: z.array(z.object({
    name: z.string(),
    description: z.string(),
    unit: z.string(),
    qty: z.number(),
    suggestedRate: z.number().nullable(),   // NULL unless user asked for pricing
    rateConfidence: z.enum(['none','low','medium','high']),
  })),
  scope: z.string(),
  deliverables: z.array(z.string()),
  exclusions: z.array(z.string()),
  paymentTerms: z.string(),
  notes: z.string(),
  termsAndConditions: z.string(),
});

const res = await anthropic.messages.parse({
  model: AI_MODELS.QUOTATION_GENERATE,     // 'claude-opus-5'
  max_tokens: 8000,
  system: [{
    type: 'text',
    text: QUOTATION_SYSTEM_PROMPT,          // stable, >512 tokens → cacheable
    cache_control: { type: 'ephemeral' },
  }],
  output_config: { format: zodOutputFormat(QuotationDraft), effort: 'medium' },
  messages: [{ role: 'user', content: buildBrief({ brief, business, customer, catalog }) }],
});
const draft = res.parsed_output!;
```

Notes that matter:
- **Prompt caching**: keep the system prompt byte-identical across requests and put it first; volatile data (customer name, brief) goes in the user turn. On Opus 5 the minimum cacheable prefix is 512 tokens. Verify with `res.usage.cache_read_input_tokens > 0` — if it's always 0, something dynamic leaked into the system prompt.
- **Thinking is on by default on Opus 5.** `max_tokens` covers thinking *plus* the response — budget generously (8000+) or you will truncate. To disable, `thinking: {type:'disabled'}` is only legal at `effort: 'high'` or below.
- **No assistant prefill** — it returns a 400 on current models. Use structured outputs instead.
- **Prices are suggestions only.** `suggestedRate` renders in the UI as a labelled chip ("AI suggestion — ₹5,000 — [Use] [Ignore]"). Nothing enters a money field without a click.

### 6.4 AI Invoice Assistant
Line-item descriptions from a short instruction; improve existing product/service descriptions (text only — price is untouchable); generate polite reminder / overdue reminder / thank-you / follow-up messages; summarize what the invoice covers as a customer-facing note.

### 6.5 AI editing command bar — the deterministic/generative split

This is the highest-risk feature to get wrong. Use **tool calling** so the model *classifies and parameterizes* the command while your code performs the mutation:

| Command | Handler | Who computes |
|---|---|---|
| "Give 5% discount" | tool `set_discount({ scope, pct })` | **Your code.** `computeTotals` re-runs. |
| "Add GST 18%" | tool `set_tax_rate({ scope, pct })` | **Your code**, after confirmation. |
| "Change delivery to 15 days" | tool `edit_text({ field:'scope', instruction })` | Model rewrites *wording only*. |
| "Make it more professional" | tool `edit_text({ field, instruction })` | Model. |
| "Translate this quotation to Hindi" | tool `translate({ targetLang })` | Model — with an explicit instruction to preserve every number, currency symbol, date, and document identifier verbatim. |

Then: render a **preview / diff** (before → after, with a totals delta banner) and require **Apply** for anything touching money. This satisfies the spec's "show a preview/diff before applying significant AI changes."

### 6.6 Cost logging

```ts
await logAiUsage({
  businessId, userId, feature: 'quotation_generate',
  model: res.model,
  inputTokens:  res.usage.input_tokens,
  outputTokens: res.usage.output_tokens,
  cacheReadTokens:     res.usage.cache_read_input_tokens,
  cacheCreationTokens: res.usage.cache_creation_input_tokens,
  estimatedCostUsd: estimateCost(res.model, res.usage), // price table in lib/ai/pricing.ts
  latencyMs, status: 'ok',
});
```
Keep `lib/ai/pricing.ts` as a per-model rate table with a comment recording the date it was last verified.

Acceptance
- [ ] An unauthenticated POST to any `/api/ai/*` route returns 401 and makes **zero** provider calls.
- [ ] Exhausting the free allowance returns 402 with an upgrade CTA; the 16th request does not reach Anthropic.
- [ ] 20 requests in 10 seconds → 429 after the configured threshold.
- [ ] Every AI request appears in `ai_usage_logs`, including failures and refusals.
- [ ] "Give 5% discount" changes the discount field and totals **without** the model emitting a single number into a money field.
- [ ] Hindi translation preserves all digits, ₹ symbols, dates, and the quotation number byte-for-byte.
- [ ] No `ANTHROPIC_API_KEY` reference exists anywhere under `app/(app)` or `components/`.

- [ ] Rate limiting on auth, AI, PDF, share, and webhook endpoints.
- [ ] Razorpay signature verification + replay/idempotency + reconciliation job.
- [ ] RLS verified per table with an automated test suite.

# 6. Explicitly deferred to V2 (per the spec — do not build these now)

Recurring invoices · AI Business Assistant over real database data · WhatsApp share/reminder integration · Customer self-service portal · Deeper cohort analytics.

**Avoid entirely for now:** full expense accounting, GST filing/compliance engine, payroll, inventory, complex CRM automation, multi-company enterprise permissions.

When you do build the V2 AI Business Assistant ("Which invoices are overdue?", "Compare this month with last month"), the rule from the spec is architectural: answers must be **computed from the user's authorized database records** via tool calls that run parameterized SQL under RLS. The model explains the numbers your code returns — it never produces a business fact itself.
